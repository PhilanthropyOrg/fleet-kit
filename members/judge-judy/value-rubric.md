# Value rubric

One rubric, two readers: judge-judy's value gate puts the two sections below into its prompt as they stand
(judge-judy.sh), and G scores every Owner decision with this file (Reif 11-02). Change it here only; never copy it.
Each risk is scored 0-3 (0 none, 1 weak, 2 solid, 3 best in class) with one line of why.

## The four risks
- value: will people want it? Utility (a real person gets what they came for, or saves a step), delight (Kano: basic, performance or delighter), and cuts (code, steps or pages removed with no loss of value earn points; a pure refactor that cuts code scores here). Score reach times depth, with today's reading: 3 when every visitor, or the people who pay us, meet the change on a path they take today; 2 when a named group meets it and the card reads that group's number today; 1 when a handful a day meet it, or the old way still got them there, or there is no reading; 0 when no one outside the company meets it.
- usability: can people use it? Nielsen's 10 usability heuristics and the design rules below, at 390 and 1440 wide. A person feels a change they cannot see: a first screen that loads sooner, a page that answers instead of a busy notice, a button that lands on the thing instead of a list. Those are usability, scored on the reading (milliseconds, the share of hits that got the busy page, steps cut). Set usability.visible false when a person neither sees nor feels any change (a job, a test, CI, a server-only fix with no reading a person feels), true otherwise; nothing visible scores 2 only when the why says so in those words, shows as n/a, and is left out of the points. 3 needs a felt or visible improvement with its reading or its shot.
- feasibility: can it be built and run well? Scales to every org (all 1.8M) and 10x traffic with no hand work per item; maintainable, fast, reliable, secure (ISO/IEC 25010). Your correctness findings land here. A doubt you write down is a score: a why that says unproven, not confirmed, could not open, stubbed, only part of the tests ran, or a test that reads source text instead of running the code, is a 1 until you confirm it. Confirm it (open the file, run the one test) or score the doubt; never both a doubt and a 2. Test shape is feasibility too (DevOps, PHIA-2358): a test that asserts copy or markup (a string of page text, a tag, a class name) tests the wording, not the product, and a new test file named for a ticket (test_gh1234, test_phia123) beside the route's or module's existing test file is a copy of a place we have one of; either one caps feasibility at 1, and the why names the file. A behavior test added to the existing route or module file scores as before, and a copy or wording change needs no test at all.
- viability: does it work for the business? One of a thing (one HQ at /hq, one org record everywhere), hub and spoke, every page a place to give, and our advantages: public hard-to-read data made beautiful and useful, matching donors and providers to orgs, verified org owners, a festival of giving. 3 when it moves to one of a thing (every link to one address, a copy retired, lines cut); 2 when it serves one named advantage and adds no copy; 1 when it adds a second mechanism or name beside one we have for the same job; 0 when it spends money, changes prices or legal text, or mails real orgs without the Owner's yes.

## Anchors
Anchors (real philanthropy PRs from 10-30 to 11-03; score against these, not against a default of 2). Every why names the anchor PR this one sits nearest to, in the form "like 14988", so a reader can check the call:
- value 0: 14835 adds docs/ui-rules.md, rules for this reviewer, no end user. 14824 a cache-key test guard, no named user.
- value 1: 14785 renames the paid report on the Terms page, which few read, no number moves. 14907 one line on a report changes font. 15266 sends the old account address to /hq/account: 45 visits a day, and the old address already answered (it still asks for sign-in today), so nobody who went there was lost. One of a thing is its viability score, not its value.
- value 2: 14995 the paid foundation report stops reading a blank line as 0 gifts, so buyers get a revenue bridge that closes. 14988 Workday apply links stop answering 404 for job seekers. 15255 three panels on the paid report fill in because the nightly pulls stop crashing (4 reports sold to date, 0 web rank rows today). 15267 report pages build once across workers: 3.63% of report hits got the busy page on 11-02, now they get the saved copy.
- value 3: 14970 one recovery reminder when a verified checkout expires unpaid, buyers come back and pay (checkouts recovered). 14985 drops Microsoft Clarity from every page, 378 lines cut, every visitor loads less. 15203 builds the two missing indexes every person page and people search read: the top statement on the database, 5.5M calls at 44 ms each, every visitor on those pages loads sooner. Reach is what lifts a fix from 2 to 3: every visitor, or every buyer, with the reading on the card.
- value 2, red-main fix (Operations, PHIA-2214; Paul 11-02): a PR that only turns a red DEPLOY test gate green (a test, a registry entry or a revert, no page change) while main has not deployed since a green sha scores value 2 on the deploy it unblocks. The user is the visitor the held merged fixes serve (every visitor when the body names none), the number is the held merged PRs that ship once a deploy passes, and the baseline is the hours since the last green deploy and how many merged PRs wait behind it, from the body or the DEPLOY run it names. Check that the diff touches no page; a test that is only weakened to pass is a correctness finding, not a fix. Set beneficiary.tool true; never value 3. Examples: app 15155 registers a crontab cap and fixes a test-order footer test, releasing about 20 merged PRs held since 8e156927d; app 15206 points three Jobs tests at the header Post a job link, with no deploy since 07:37 UTC.
- value 2, measuring tools (G, PHIA-2043): a PR that changes no page but makes points, pay or the gate follow one visitor number already measured today (a kpi_daily metric such as jobs/applies, dash_metric_points, Search Console, events) scores value on that number: 2 when the PR names that one number and where it is read, as before when it names none. Set beneficiary.tool true for these; a tool PR is never value 3. Correctness, feasibility and research are judged in full. Example: box 247 pays the second half of a PR's points only when jobs/applies moved after merge.
- value 2, Owner-asked cost (G, PHIA-2067 and PHIA-2070): a PR that cuts CI or platform cost the Owner asked for scores value on platform/ci_usd_per_day (GitHub billing usage, the Automation watch list) or platform/fix_pr_wait_hours (median hours from a fix PR opening to merge). Here the user is the Owner, who pays the bill and waits for fixes. It is 2 when the PR names one of those numbers and how much it should fall, and as before when it names neither. Set beneficiary.tool true; never value 3. Example: app 15042, which cuts CI minutes per merged PR.
- usability 0: a person can no longer reach or read what they came for (a page 500s, a button does nothing, a new top-level section on a designed report, rule 1).
- usability 1: it works but adds a second name for one thing or a new box where one line would do (rules 3 and 4). Also: a change on a page or in a mail a person meets, with no shot of it at 390 and 1440 (or of the mail) in the PR: the reviewer cannot say it follows the rules, so it does not score as if it did.
- usability 2 (visible true): a visible or felt change that follows the design rules and shows its shots, but a visitor would not call it better. Nothing a person sees or feels is visible false and scores 2 with the why saying so, not this 2.
- usability 3: 14896 hub pages on a phone show the list on the first screen, two lines a row. 14967 long hub rows wrap instead of being cut off. 15203 every person page's first screen comes sooner, 44 ms off the slowest read on every view, with the reading in the body: felt, not seen, and still a 3.
- feasibility 0: a correctness defect you block on. 1: hand work per item or a fix that will not last (14940 bumps a page cache key by hand to make a price show). 15255's guard test reads the source text for the old pattern instead of running the three queries on Postgres, and the bug it fixes was exactly a Postgres-only crash no test caught: a doubt the reviewer wrote down, so 1 until a test runs the queries. 15267 as first reviewed: the warm-ahead date syntax was called unproven on Postgres and the aging path stubbed in tests; a named doubt is a 1 until confirmed. Also 1, test shape (DevOps, PHIA-2358; the same rule ends every seat charter, box PR 288): a PR that adds a test asserting copy or markup, or a new test file named for a ticket (test_gh1234.py, test_phia123.py) when the route's or module's test file exists, is a 1 whatever the product change earns, and the why names the test file and the line that would lift it (fold the test into the existing file, or drop a copy test). Why: the suite grew from about 590 tests on 9-17 to 11,654 on 11-02, 83% of the 517 files added in 14 days were one-ticket files, and all of the last 20 red deploys were fixed by editing a test, not the product (9 of them copy or markup checks). A behavior test in the existing file is never scored down for its shape. 2: works and is tested at today's size, with no doubt left in the why. 3: 14952 a cached report no longer waits behind cold builds, so it holds at 10x traffic. 15203 removes a full table scan on every request (5.5M scans of 94k rows, 102k scans of 2M rows), so the same pages hold at 10x.
- viability 0: 14431 a live cron that changes Stripe billing and mails price changes before the Owner approved it. 1: a second copy of a thing we already have one of, or a second mechanism beside the one we have for the same job. 2: neutral for the business, serving one named advantage and adding no copy. 3: 14989 Billing drops its own verify cards for the one verify card on Home, one of a thing, 192 lines cut. 15266 points every account link in the app at the one /hq/account and 301s the old address: one HQ, no second name left alive in the app.
A score of 2 is a claim, not a default: every why says what would make it a 3, and that must be something this PR could have carried (a line in its diff, a test it could run, a reading its card could give), never a different PR and never a lift that only the 48-hour read can show. A table of 2/2/2/2 that does not say what would make each a 3 is a wrong answer. When all four come out 2, that is the sign you scored the default: go back to each axis, name the anchor PR it sits nearest to, and keep the 2 only where the why names one. The last 8 reviews should not share one score set 5 times (value_judge.py flat); if yours do, the scores are not reading the PRs.
