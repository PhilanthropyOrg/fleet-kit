# Value rubric

One rubric, two readers: judge-judy's value gate puts the two sections below into its prompt as they stand
(judge-judy.sh), and G scores every Owner decision with this file (Reif 11-02). Change it here only; never copy it.
Each risk is scored 0-3 (0 none, 1 weak, 2 solid, 3 best in class) with one line of why.

## The four risks
- value: will people want it? Utility (a real person gets what they came for, or saves a step), delight (Kano: basic, performance or delighter), and cuts (code, steps or pages removed with no loss of value earn points; a pure refactor that cuts code scores here). Score reach times depth, with today's reading: 3 when every visitor, or the people who pay us, meet the change on a path they take today; 2 when a named group meets it and the card reads that group's number today; 1 when a handful a day meet it, or the old way still got them there, or there is no reading; 0 when no one outside the company meets it.
- usability: can people use it? Nielsen's 10 usability heuristics and the design rules below, at 390 and 1440 wide. A person feels a change they cannot see: a first screen that loads sooner, a page that answers instead of a busy notice, a button that lands on the thing instead of a list. Those are usability, scored on the reading (milliseconds, the share of hits that got the busy page, steps cut). Set usability.visible false when a person neither sees nor feels any change (a job, a test, CI, a server-only fix with no reading a person feels), true otherwise; nothing visible scores 2 only when the why says so in those words, shows as n/a, and is left out of the points. 3 needs a felt or visible improvement with its reading or its shot.
- feasibility: can it be built and run well? Scales to every org (all 1.8M) and 10x traffic with no hand work per item; maintainable, fast, reliable, secure (ISO/IEC 25010). Your correctness findings land here. A doubt you write down is a score: a why that says unproven, not confirmed, stubbed, only part of the tests ran, or a test that reads source text instead of running the code, is a 1 until you confirm it. You have no shell and run nothing: confirm it by reading the diff and the changed files printed whole after it, or score the doubt; never both a doubt and a 2. A file the prompt does not show is not a doubt about the PR. Test shape is feasibility too (DevOps, PHIA-2358): a test that asserts copy or markup (a string of page text, a tag, a class name) tests the wording, not the product, and a new test file named for a ticket (test_gh1234, test_phia123) beside the route's or module's existing test file is a copy of a place we have one of; either one caps feasibility at 1, and the why names the file. A behavior test added to the existing route or module file scores as before, and a copy or wording change needs no test at all.
- viability: does it work for the business? One of a thing (one HQ at /hq, one org record everywhere), hub and spoke, every page a place to give, and our advantages: public hard-to-read data made beautiful and useful, matching donors and providers to orgs, verified org owners, a festival of giving. 3 when it moves to one of a thing (every link to one address, a copy retired, lines cut); 2 when it serves one named advantage and adds no copy; 1 when it adds a second mechanism or name beside one we have for the same job, and at most 1 when it adds a second copy of something we built (an org search or typeahead, an org lookup, a pick log, a card frame, a mail sender) instead of calling the one we have; the why names the existing code to call (for org search, /990/api/suggest), and a 1 sends the work back (Reif 11-03: reuse what we built, changed in place for every app, so two customers make one service better); 0 when it spends money, changes prices or legal text, or mails real orgs without the Owner's yes.

## Anchors
Anchors (real philanthropy PRs from 10-30 to 11-03; score against these, not against a default of 2). Every why names the anchor PR this one sits nearest to, in the form "like 14988", so a reader can check the call:

A staff screen, a server fix and a test fix each have their own anchor below; none of them is 14824.
- value 1: 14785 renames the paid report on the Terms page, which few read, no number moves. 14907 one line on a report changes font. 15266 sends the old account address to /hq/account: 45 visits a day, and the old address already answered (it still asks for sign-in today), so nobody who went there was lost. - value 2: 14995 the paid foundation report stops reading a blank line as 0 gifts, so buyers get a revenue bridge that closes. 14988 Workday apply links stop answering 404 for job seekers. 15255 three panels on the paid report fill in because the nightly pulls stop crashing (4 reports sold to date, 0 web rank rows today). 15267 report pages build once across workers: 3.63% of report hits got the busy page on 11-02, now they get the saved copy.
- value 3: 14970 one recovery reminder when a verified checkout expires unpaid, buyers come back and pay (checkouts recovered). 14985 drops Microsoft Clarity from every page, 378 lines cut, every visitor loads less. 15203 builds the two missing indexes every person page and people search read: the top statement on the database, 5.5M calls at 44 ms each, every visitor on those pages loads sooner. Reach is what lifts a fix from 2 to 3: every visitor, or every buyer, with the reading on the card.
- value 2, red-main fix (Operations, PHIA-2214; Paul 11-02): a PR that only turns a red DEPLOY test gate green (a test, a registry entry or a revert, no page change) while main has not deployed since a green sha scores value 2 on the deploy it unblocks. The user is the visitor the held merged fixes serve (every visitor when the body names none), the number is the held merged PRs that ship once a deploy passes, and the baseline is the hours since the last green deploy and how many merged PRs wait behind it, from the body or the DEPLOY run it names. Check that the diff touches no page; a test that is only weakened to pass is a correctness finding, not a fix. When the body names the red run or the red-main task but gives no hours and no PR count, the run it names is the baseline and the score is still this 2, with the why asking for the count: a red-main fix is never 14824 (PHIA-2780: 15508 clears a cached peer pool between tests under fast-lane PHIA-2735, names run 41886538761, and was scored 1 for a missing hours line). Set beneficiary.tool true; never value 3. Examples: app 15155 registers a crontab cap and fixes a test-order footer test, releasing about 20 merged PRs held since 8e156927d; app 15206 points three Jobs tests at the header Post a job link, with no deploy since 07:37 UTC.
- value 2, measuring tools (G, PHIA-2043): a PR that changes no page but makes points, pay or the gate follow one visitor number already measured today (a kpi_daily metric such as jobs/applies, dash_metric_points, Search Console, events) scores value on that number: 2 when the PR names that one number and where it is read, as before when it names none. Set beneficiary.tool true for these; a tool PR is never value 3. Correctness, feasibility and research are judged in full. Example: box 247 pays the second half of a PR's points only when jobs/applies moved after merge. The same holds for a counter, lane tag or log that reads the visitor number a `judge-yes` card's Guess names, when the card names that measuring step as its own (the Judge, PHIA-2622): the user is the card's User, the number is the card's number with its reading, and it is value 2. Example: app 15305 counts report hits that got the busy page by lane, the 3.56% share the PHIA-2499 card reads and names as step 1. It was scored 1 "like 14824" four times; 14824 is a guard with no named user or number, and a step the Judge's YES already priced is not that. A `judge-yes` card's User and number are the beneficiary; the PR's value drops under the Judge's call only when the PR ships less than the card's step, with the why naming the card line it leaves out.
- value 2, Owner-asked cost (G, PHIA-2067 and PHIA-2070): a PR that cuts CI or platform cost the Owner asked for scores value on platform/ci_usd_per_day (GitHub billing usage, the Automation watch list) or platform/fix_pr_wait_hours (median hours from a fix PR opening to merge). Here the user is the Owner, who pays the bill and waits for fixes. It is 2 when the PR names one of those numbers and how much it should fall, and as before when it names neither. Set beneficiary.tool true; never value 3. Example: app 15042, which cuts CI minutes per merged PR.
- value 2, Owner-asked staff work (Automation, PHIA-2064): a PR on a staff-only screen (superadmin, the console, the Owner page) that does what the Owner asked in a gh issue or board task the PR body or task links scores value 2. Here the user is the Owner (or the staff the ask names), and the number is the one the ask or the body names (clicks to reach a number, a headline that disagrees with its rows, hours to a staff reply). Name both in beneficiary. With no linked Owner ask, a staff-only screen is value 1 at most, as before. Staff work that lets staff answer or serve outside users (claimants waiting on a reply, report buyers waiting on a review) is scored on those outside users like any PR, not here: name them and the count waiting, and do not cap it. Set beneficiary.tool true; never value 3. Example: app 15064 folds the console Analytics page into Overview, as the Owner asked in gh 13473. The link is any of: a gh issue, a PHIA task in the title or body (`G ask: PHIA-2644`), or the task facts line saying the task was filed by the Owner or carries `judge-yes`; a board task the Owner filed is the Owner's ask, and a Judge YES is a decision already made, so neither needs a gh issue. Example: 15428, the staff HQ Jobs list of every application, closes PHIA-2644, which the Owner filed and the Judge labelled judge-yes; it was scored 1 twice on 11-04 for "no linked issue" (PHIA-2780), and is a 2 here. Outside-facing work that does what a linked Owner-filed issue asks (a cruft fix in member mail, gh 13752; 15505 sends paid-post applicants on to the employer's form, PHIA-2767, 9 of 191 applications named) is value 2 at least when the body names the users and how many meet it; the Owner already judged it worth doing, so the handful rule does not pull it to 1.
- value 2, production watch (Automation, PHIA-2064): a fix that makes a dark or failing production page someone sooner (an alert that now fires, a probe that is now watched) scores value on the visitors an outage hits: the user is those visitors, the number is minutes until the team knows (Automation's time to detect a dark production, target under 5). It is 2 when the body names the probe and the detect time before and after. Set beneficiary.tool true; never value 3. Example: app 15133 pages after 3 failed pg_health probes in a row. The same holds for a fix that stops false pages, so real ones are not buried: the number is false pages a day, and the body must name the real cases it still pages on (app 15195: about 1.5 false money pages a day stop, while failed cards and paid-with-no-plan still page).
- value 2, database load (the Judge, PHIA-2780): a fix to a statement at or near the top of pg_stat_statements, with its reading from prod in the body (calls, mean time, an EXPLAIN), is scored on every visitor who shares that database, as 15203 is: the user is those visitors, the number is the statement's calls times its mean time a day, before and after. 2 when the body carries the prod reading; 3 when the statement runs on a page every visitor meets and the body reads that page (15203, 44 ms off every person page). A server fix with a reading has a user who feels it (the usability line says so), so it is never 14824 and never "no outside user". Examples: 15511 stops the empty-states card re-reading 14 days of rows on every Overview build, the heaviest statement on the database (5,094 calls at 13.5 s, EXPLAIN on prod 11-04); 15510 sorts 14 dash_events reads by the index order (2,600 ms to 0.1 ms a read on the HQ feed and the console). Both close the Owner-filed fast-lane PHIA-1812 (p95 latency alerts) and both were scored 1 "like 14824" on 11-04.
- cuts: a PR that only removes something is scored on the dead weight it takes off a named user's path, never sent to value 1 for adding nothing. Dropping an unlinked link, a stale count or a second name from a page or mail those users read is value 2 when the body names the users and how many meet it. Example: app 15099 cuts an unlinked contact line from about 7,000 member mails a month.
- re-looks (Reif 11-05, PHIA-2965): a live page looked at again long after it was built, and improved, simplified, clarified, given less text, or a step skipped, is worth shipping on its own; no kpi number has to move at review time, since the 48-hour read is what pays the second half. The page's number is today's visits on the URL or page family (Search Console or site/human_visits), read in the body or on the card; with no reading, value 1 as always. Less text or a skipped step is a cut: scored on the cuts line above, value 2 when the body names the page family, how many a day meet it and what was cut (lines, words or the step), cut true and paid in full at merge. Improved, simplified or clarified scores value on reach (2 when the body reads the family's visits today, 3 when every visitor meets the page) and usability on the 390 and 1440 before-and-after shots in the PR: 3 when a visitor would call the after better, 2 when it follows the rules and they would not, 1 with no shots as always; metric is the next step the page leads to (jobs/applies, claims/claim_cta_impressions, 990/search_clicks) or site/human_visits, with a small guess, never 0. A change made only to touch a file (a style rule merged, a token declared, a guard widened), with no shot a visitor can tell apart and no visits reading, is value 1 like 14907 (one line changes font) however many commits or templates it spans: a commit that counts as a look is not a user. Example: 15595 (PHIA-2889) changed 11 templates in 11 commits so each counted as a look; a re-look PR scores on the reading and the shots it carries, not on the commit count, and the why says which of the two it lacks.
- usability 0: a person can no longer reach or read what they came for (a page 500s, a button does nothing, a new top-level section on a designed report, rule 1).
- usability 1: it works but adds a second name for one thing or a new box where one line would do (rules 3 and 4). Also: a change on a page or in a mail a person meets, with no shot of it at 390 and 1440 (or of the mail) in the PR: the reviewer cannot say it follows the rules, so it does not score as if it did.
- usability 2 (visible true): a visible or felt change that follows the design rules and shows its shots, but a visitor would not call it better. Nothing a person sees or feels is visible false and scores 2 with the why saying so, not this 2.
- usability 3: 14896 hub pages on a phone show the list on the first screen, two lines a row. 14967 long hub rows wrap instead of being cut off. 15203 every person page's first screen comes sooner, 44 ms off the slowest read on every view, with the reading in the body: felt, not seen, and still a 3.
- feasibility 0: a correctness defect you block on. 1: hand work per item or a fix that will not last (14940 bumps a page cache key by hand to make a price show). 15255's guard test reads the source text for the old pattern instead of running the three queries on Postgres, and the bug it fixes was exactly a Postgres-only crash no test caught: a doubt the reviewer wrote down, so 1 until a test runs the queries. 15267 as first reviewed: the warm-ahead date syntax was called unproven on Postgres and the aging path stubbed in tests; a named doubt is a 1 until confirmed. Also 1, test shape (DevOps, PHIA-2358; the same rule ends every seat charter, box PR 288): a PR that adds a test asserting copy or markup, or a new test file named for a ticket (test_gh1234.py, test_phia123.py) when the route's or module's test file exists, is a 1 whatever the product change earns, and the why names the test file and the line that would lift it (fold the test into the existing file, or drop a copy test). Why: the suite grew from about 590 tests on 9-17 to 11,654 on 11-02, 83% of the 517 files added in 14 days were one-ticket files, and all of the last 20 red deploys were fixed by editing a test, not the product (9 of them copy or markup checks). A behavior test in the existing file is never scored down for its shape. 2: works and is tested at today's size, with no doubt left in the why. 3: 14952 a cached report no longer waits behind cold builds, so it holds at 10x traffic. 15203 removes a full table scan on every request (5.5M scans of 94k rows, 102k scans of 2M rows), so the same pages hold at 10x. Tool PRs (CI, a test, a script, a cron; usability.visible false) have their own 3, since 10x traffic never applies to them: 3 when the body carries the proof on the real tree (the CI run that went green with the fix, a flaky test run 10 times green, the smoke set's file count on today's tree), 2 when the test runs the real function on stubbed or injected sources only, 1 when a doubt stays. "A 3 would need a test on the real database write" is a line the PR could have carried; "holds under load" on a test file is not, and a why that names a 3 this PR could not carry is the default (PHIA-2622: 15361, 15358 and 15364 all sat at 2). The same goes the other way: a why that writes a doubt and keeps the 2 is the default too. 15511's why said two older tests still patch collect with a lambda that no longer takes the new argument, so they pass vacuously: that is a doubt written down, a 1 until confirmed, and the 2 it kept was wrong (PHIA-2780).
- viability 0: 14431 a live cron that changes Stripe billing and mails price changes before the Owner approved it. 1: a second copy of a thing we already have one of (a new org search beside /990/api/suggest), or a second mechanism beside the one we have for the same job. 2: neutral for the business, serving one named advantage and adding no copy. 3: 14989 Billing drops its own verify cards for the one verify card on Home, one of a thing, 192 lines cut. 15266 points every account link in the app at the one /hq/account and 301s the old address: one HQ, no second name left alive in the app. Tool PRs (CI, a test, a script, a cron) are scored on one of a thing in the tooling, where "neutral for the business" is the default this rubric forbids: 3 when the diff retires a mechanism (a fixed wait, a duplicate check, a workflow step, a second script) with the lines cut named in the why; 2 only when the why names the one existing file the diff extends (the module's test file, the one smoke selector, the one gh-pr-view read) and the diff adds no file; 1 when it adds a script, cron, workflow or test file beside one we have for the job, or leaves the old mechanism alive beside the new one. 15364 keeps the 250 ms and 300 ms waits it could have replaced in the same file: a 2 whose 3 was in reach, not a 3. The lines cut are named, never netted against the lines added: 15508 folds a per-file fixture into conftest beside the other per-process resets and removes the per-file copy, so one mechanism remains; that retired copy is the 3, and "adds about as many lines as it removes" is not a reason to hold it at 2 (PHIA-2780).
A score of 2 is a claim, not a default: every why says what would make it a 3, and that must be something this PR could have carried (a line in its diff, a test it could run, a reading its card could give), never a different PR and never a lift that only the 48-hour read can show. A table of 2/2/2/2 that does not say what would make each a 3 is a wrong answer. When all four come out 2, that is the sign you scored the default: go back to each axis, name the anchor PR it sits nearest to, and keep the 2 only where the why names one. The last 8 reviews should not share one score set 5 times (value_judge.py flat); if yours do, the scores are not reading the PRs. 1/2/2/2 is the tool-PR default, as 2/2/2/2 is the page default (PHIA-2622: 5 of 8 on 11-03, four of them CI or test PRs; PHIA-2780: 5 of 8 again on 11-04, 15428, 15505, 15508, 15510 and 15511, three of them on tasks the Owner filed and one with the Judge's yes): value 1 "like 14824", usability n/a, and 2 on the rest because "it works and adds no second mechanism". The task facts line above the card says who filed the task and which labels it carries; read it before value, and score the anchor it points at (Owner-asked, judge-yes, red-main, database load) rather than the user's seat. Nothing visible is a fixed slot, so on a tool PR the spread has to come from the other three: name the tool anchors above (a judge-yes card's step is 2, not 14824's 1; proof on the real tree is a feasibility 3; a mechanism retired is a viability 3, a file added is a 1), and keep a 2 only where the why names the diff line that would have moved it.
